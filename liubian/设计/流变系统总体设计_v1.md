## 1. 定位
流变系统 = 智能体基础设施集合体，统一承载 记忆 / 被炉 / 更新 / 通路 四类能力。
「流变」取义：记忆会流动、系统持续演化。

## 2. 子系统构成
| 子系统 | 内部名 | 职责 | 现有资产 |
|---|---|---|---|
| 流变·记忆 | liubian-memory | 日记/标签/共现/检索/用户/留言板 | memory-skill、memory.py |
| 流变·被炉 | liubian-kotatsu | 实时聊天室/UI/待办/定时/钩子 | kotatsu 命令、kotatsu_ui.py |
| 流变·更新 | liubian-update | 技能版本/独立装载/快照 | auto-updater、tracker.json、agent_versions |
| 流变·通路 | liubian-path | 双通路问答：分解检索/外部校验/汇聚 | （新建） |

## 3. 分层架构
- 接入层：主智能体（Codex 内）、真人管理员（被炉 UI，免密）
- 协议层：通路二外部 API 契约、被炉消息协议、留言板协议
- 服务层：liubian 统一 CLI（memory/kotatsu/update/path 四组子命令）、被炉 server/UI、通路二工具
- 存储层：全局注册表 .liubian_registry/、各工作区 <工作区>/liubian/、技能快照 .skill_tracker/

## 4. 用户与权限
- 全局唯一注册表：花名 + 8 位数字密码 + 哈希密钥（每用户独立哈希锁）
- 三类主体：真人管理员（免密/UI 专用）、智能体（花名账户）、外部工具（无账户，仅通路二 API 调用）
- 注册入口统一收口到流变系统；记忆与更新双端用户名互通、全局防重名

## 5. 核心数据流
### 5.1 每轮对话（流变·记忆）
写上一轮日记 → 查留言板 → 检索 → 回答（每轮一篇日记，格式：日记/留言/搜索 + 正文）

### 5.2 复杂问题（流变·通路，单轮内完成）
分解大问题为子问题 → 逐子问题用 tag 组检索记忆 → 调用通路二工具（并发两个无上下文外部 API：初始回答 + 问题清单）→ 汇聚（记忆总结 + 初始回答 + 问题清单）→ 最终回答 → 一篇日记

### 5.3 技能更新（流变·更新）
#update → agent check（比对 agent_versions vs tracker.json）→ 通读变更 → sync 哈希

### 5.4 被炉（流变·被炉）
join 建房间 → 留言板通知 → 实时对话 → 每 10 条消息创始人记日记 → UI 实时刷新/待办/检索

## 6. 成本原则
- 主智能体调用吃缓存（现 99%）：保持固定前缀（技能文本 + 记忆流程格式）
- 通路二外部 API 用廉价模型（如 flash），每轮固定 2 次调用，无上下文继承
- 每轮记忆材料限长（记忆总结压缩为每条一句话），控制主上下文膨胀

## 8. 通路二工具契约（新建，一次性无状态产品）
- 脚本：liubian_path2.py
- 入参：原问题文本
- 行为：并发调用 外部API-A（生成初始回答） + 外部API-B（检验并列出问题）
- 出参 JSON：{ initial_answer, problems: [{问题, 位置, 理由}] }
- 无上下文、不继承、不写记忆、不检索

# 流变系统 总体设计 v2（2026-08-12 管理员确认版）

## 已确认决策
1. **不额外改名**：记忆系统是流变系统的子系统，技能文件夹保持 `memory-skill` 原名，物理目录不更名。
2. **通路二使用两个不同的外部 API**：用于确认两个通路消耗的 token 量；两 API 独立配置，默认
   - API-A（初始回答）：deepseek-v4-flash
   - API-B（检验）：google/gemini-3-flash-preview
   - 每次调用用量（prompt/completion/total/cache/latency）记录到 usage_log.jsonl
3. **通路对所有问题触发**：不再区分简单/复杂，统一走 分解→检索→通路二→汇聚。
4. **迁移期尽量保证兼容**：旧命令继续可用；新统一入口对旧命令透传，避免大范围改动。
