## 2. 派生规则（消费方自算 hash 必须逐字对齐——标准 §8 同源派生函数纪律）

```
name    = String(raw).trim().normalize('NFC')
          （非空；≤64 字符；不含控制字符；不以 '@' 或 '#' 开头）
name_key = name.toLowerCase()               ← 大小写不敏感唯一
hash     = SHA256(UTF-8(name)) 小写 hex      ← 64 位，全局唯一标识符
short_id = hash 的最短唯一前缀，长度 ≥8       ← git 式；无碰撞时恰为 8
```

- 短 ID 随表演化：新注册若造成 8 位前缀碰撞，**相关条目一并自动扩位**（最小 9 位，依此类推）。
- 消费方**不要自己缓存 long-lived 的 short_id 推导逻辑**——要 hash 用 §3 只读接口查，short_id 仅作展示/路由。

### 2.1 改名语义（v1.1；v0.3.0 实现；管理员 2026-10-01 联合任务 · B1 模型）

**核心不变式：hash 是账号 ID，注册时派生、此后不可变；name 是可变展示名。**

```
rename(旧名|hash, 新名) →
  identities.name/name_key 更新（新名仍走 §2 全套归一与唯一校验）
  hash / short_id / created_at / workspace / note / status 一律不变
  旧名写入 name_aliases（历史名，lookup 回查命中并指向现名）
  写一行 renames 账目（hash, old, new, at, actor, note）
  bindings 中的名字副本同事务同步更新
```

- **为什么 hash 不变**：wiki 修订账目、留言板 `from_reg`、房间历史署名都引用 `名字#短ID`；hash 一变，全部历史引用失配。
- **旧名不可被二次注册**：旧名的 hash 仍归原身份（hash 由名字派生），`register` 以「历史名」拒绝并提示现名。
- **改回自己的历史名**：允许；该名随即从别名表摘除（不再是"历史"）。
- **占用他人历史名**：拒绝。**停用（retired）身份不可改名**。
- **拒绝即零写入**：全部校验在写入前完成；写入包事务，半途失败回滚。
- 消费方注意：**昵称一律读取时按 hash 解析**（或订阅变更），不要长期缓存名字副本——被炉旧成员记录占名事故（2026-10-01）即"名字副本两处真相"所致。

## 3.1 会话↔身份独热绑定（v0.2.0，管理员 2026-10-01 钉）

- **对话哈希**：`SHA256(sessionId)` 前 8 位十六进制——与被炉 `idFor` 同源同配方（标准 §8），被炉房间 ID 即本值。
- **独热配对**：一个会话至多绑定一个身份，一个身份至多绑定一个会话（`bindings` 表 session_hash 主键 + name 唯一索引双向强制）。旧会话终结后重绑：先 `unbind` 释放再 `bind`。
- **注入行为**：未绑定会话在每个新人类回合收到**一条**注册提示（含本会话哈希 + 两步指引）；已绑定会话**不注入**。注册中心不可用时静默降级不注入（门禁③）。总开关 `bindNag`（默认开）。
- **绑定前提**：名字必须已注册且未停用（bind 不代注册）。
- **存储**：同 `registry.db`：

```sql
bindings(
  session_hash TEXT PRIMARY KEY,   -- 8 位会话哈希
  name TEXT NOT NULL UNIQUE,       -- 独热：一个身份至多一个在绑会话
  bound_at TEXT NOT NULL, note TEXT
)
```

- **绑定即归因**：绑定后该会话产生的署名/贡献者行为归因到绑定身份（wiki S3、便签 P2 的数据源）。
- **归属校验**：注入钩子每回合登记会话→工作区（`session_seen` 表）；bind 时若身份已登记归属且会话实际工作区可判定，两者不符即拒绝（防止 A 工作区的会话绑走 B 工作区的身份）。身份未登记归属或会话工作区不可判定时不拦（不误伤）。

## 5.1 被炉实现参考（白泽章节，2026-10-01 交付）

> 被炉是被炉侧"会话派生运行身份"的现行参考实现。与注册中心的关系：**正交互补**——注册中心管"跨会话持久身份"（全局唯一名+哈希），被炉本地管"会话作用域运行身份"（ID 随会话生死）。留言板/P2P 接入时：发帖人/参与者字段挂注册中心的持久名，路由/会话级查找用被炉本地 ID。

- **会话 ID 派生**：`SHA256(会话号) 前 8 位十六进制`；8 位碰撞时扩位到 12（构造性防碰撞，与 §2 短 ID 扩位同思路，但派生源是会话号而非名字）。
- **昵称作用域**：**房间内唯一**（§1 定案的"房间内唯一归被炉本地"）——重名自动加 `-2/-3…` 后缀，最终名回传给注册者。
- **昵称来源优先级**：显式指定 > 工作区名 > 短 ID；昵称可随 join 更新。
- **与注册中心的对接点**：被炉昵称（展示层）可引用注册中心持久名；留言板/P2P 上线后，发帖人/参与者身份字段直接用注册中心的 `name + #short_id`。

## 8. 删除与跨系统同步（v1.2，管理员 2026-10-01 裁定）

### 8.1 三层语义（两层正交，别混成一个动作）

| 层 | 语义 | 动什么 | 不动什么 |
|---|---|---|---|
| **L1 退出房间**（`leave`，被炉侧） | 退房 ≠ 销号 | 只清被炉房间登记 + 投递游标 | 注册中心一切 |
| **L2 删除运行身份**（`forget`） | 清这个会话在各系统的运行态 | 基建 `bindings` 解绑 + `session_seen` 清；被炉成员/游标/副手/模式；便签池 | **持久名**（仍在册） |
| **L3 注销持久名**（`retire`） | 名字独热保留、历史引用不断裂 | `identities.status=retired` | 历史账目（wiki 修订**绝不改**） |

**管理员裁定（2026-10-01）：删除账号 ⇒ L1 + L2 + L3（一并 retire）。**
⚠ 但**接口默认是 `retireName=false`**——名字独热**不回收**，retire 等于**永久烧掉一个名字**，必须先想清楚：
「**接口默认**」与「**产品语义**」分开写，消费方（被炉 `account delete`）**显式传 `retireName: true`**。

### 8.2 墓碑：为什么必须有

只删 `bindings` 行**不足以**表示"此人已删"：消费方（被炉 C1）查不到绑定时会**回落本地昵称副本** → 登记还在、下次活动照旧。
→ **墓碑优先于降级**（本契约的硬口径）：

| 读取结果 | 判定 | 消费方行为 |
|---|---|---|
| 注册中心**不可达**（读库异常） | `reachable=false` | 允许回落本地副本（离线降级） |
| 命中但身份 `status≠active` | 已注销 | **禁止回落**，标"已注销"，交删除流程清理 |
| 命中墓碑 `op='forget'` | 已删除 | **禁止回落/自动重建** |

**墓碑 = 硬拒（管理员 2026-10-01 21:1x 裁定，取代本契约初稿与本文件早前"允许显式再注册"的口径）**：
删除之后**连显式 `join` 也拒**，不留复活入口——`join`、`mode`（开启被炉模式是另一条隐式入房路径）等一切入房入口都必须查墓碑并拒绝。
**唯一复活通道 = 管理员在基建侧执行 `revive`**（工具动作）；消费方**跟随 `lift` 事件**解除各自的本地墓碑。消费方**不得**在 join 路径上调 `liftTombstone` 自救。

### 8.3 表与接口（v0.4.0）

```sql
-- 只增不改（与 renames 同纪律）：当前状态 = 该 session 中 id 最大的那行
tombstones(id INTEGER PRIMARY KEY AUTOINCREMENT, session_hash, op -- 'forget'|'lift'
           , at, actor, reason)
```

```js
const svc = ctx.reflect.get('liubianInfra')
await svc.forgetSession({ sessionHash, actor, reason, retireName = false })
// → { ok, sessionHash, tombstone: true, alreadyForgotten, unbound: 0|1, name, retired: false|'retired'|'already-retired', at }
await svc.liftTombstone({ sessionHash, actor, reason })   // → { ok, lifted, alreadyActive? }
await svc.isForgotten({ sessionHash })                    // → { ok, forgotten }（单点查询，消费方不必拉全量事件流）
await svc.changes({ since = 0 })
// → { ok, seq, identities:[全量], bindings:[全量], tombstones:[id > since], forgotten:[当前墓碑态的会话] }
```

- **新增 `forgotten` 快照（本契约定稿后补，消费方实测暴露的缺口）**：`changes()` 除事件增量外，**再带一份"当前仍处于墓碑态"的会话清单**（小表全量，与 `identities`/`bindings` 同构）。
  为什么补：消费方要回答"这个会话是不是被删了"，若只能拉 `since:0` 的全量事件流，就会踩上"**顺手推进水位 → 漏事件**"的坑。有了 `forgotten` 快照，查态与消费事件彻底分开：**查态用 `forgotten`（或 `isForgotten`），消费用 `tombstones` 增量推水位**。

- **`forgetSession`**：单事务（解绑 → 清 `session_seen` → 写 `forget` 墓碑 →（可选）retire），**幂等**；任一步失败**整单回滚**，错误折成 `{ok:false,error}` 不抛。
- **`liftTombstone`**：写一条 `lift` 事件，**不删历史**。**当前语义 = 管理员专用**（`revive` 工具动作是唯一入口）——消费方**不得**在 join 路径调它自救（§8.2 硬拒裁定）。
- **`changes`**：**小表全量快照 + 墓碑流按 id 增量**（`seq` 取墓碑表 MAX(id)）。返回 `identities` / `bindings` / `forgotten` 三份**全量快照** + `tombstones` **增量**。
  ⚠ **两个用途别混**：查"当前是否被删"读 `forgotten`（或 `isForgotten`），**不要**用 `since:0` 拉全量事件流来查态——那次调用若顺手把水位推到最后，会**漏掉之后的事件**（被炉实测踩到过这个坑，本契约因此补 `forgotten`）。
  为什么不给每个写路径都记一笔事件：现有 6 个写身份动作 + `bind`/`unbind` 都要记得 append，**漏一个就是静默漏事件**；而 `identities`/`bindings` 只有十几行，全量重读成本≈0。
  **墓碑表只增不改**（复活也是一条新事件）——若写成"一行一状态 + 更新列"，复活只改列不改 id，按水位轮询的消费方**永远看不到它**。改名/别名**不进事件流**（读取时按 hash 解析已覆盖，见 §2.1）。

| 系统 | 要清的 | 由谁 |
|---|---|---|
| 基建 | `bindings` 行 + 墓碑 + `session_seen` | 基建（`forgetSession`） |
| 被炉 | `members.byId/bySession`、`delivery` 游标、副手、被炉模式；**`board` 未读孤儿标 `orphaned`**（已读保持 read） | 被炉（消费 `changes`） |

| 博物 | **零动作**（实测 `files` 表无用户列） | — |

### 8.5 两条配套口径

1. **历史署名冻结、当前显示名实时解析**：消息行的 `from_name` 是**写入时快照**（历史显示旧名），成员簿走 C1 **实时解析**（显示现名）。同一个人的旧消息显旧名、成员簿显现名——**这不是不一致，是正确**。改名不断裂历史引用，靠的正是 hash 不变。
2. **留言板历史行保留**：`to_member` 指向已删成员是**可接受的孤儿**（显示回落 `from_name` 快照）；只有**未读**行要标 `orphaned`（否则永远算进未读角标）。

### 8.6 验收矩阵

1. 删自己 → 房间记录/游标/绑定三处清；`binding <session>` 不存在；`account status` 报无身份
2. **幂等**：再删 → `removed:0 / unbound:0`，且**不 5xx**
3. `retire` 后：`lookup <name>` → 已停用；`register <name>` → **拒**（独热保留）；`binding` → 不存在
4. **历史可读**：wiki 修订 executor、房间历史消息、`board` 行仍可读
5. **降级分辨**：注册中心**不可达** → 回落本地副本；身份 `retired` / 墓碑 → **不回落**
6. **部分失败可见**：本地成功/解绑失败 → 回执显式报出且**可重试**
7. **删除是硬拒**：删除后 stale 副本不得自动重建，**显式 `join` 也被拒**（连 `mode` 等隐式入房路径一并拒）；**唯一复活通道 = 管理员在基建侧 `revive`**，消费方跟随 `lift` 事件解除本地墓碑
8. **墓碑不被热路径擦掉**：对同一 session 连调 `noteSession` 数次后，`changes` 里墓碑仍在
9. **复活事件不漏水位**：`liftTombstone` 后，以旧 `seq` 调 `changes` 必须能看到这条 `lift`
