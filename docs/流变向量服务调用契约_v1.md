## 2. 端点契约

### 2.1 探活：`GET /health`
- 200 = 在线；任何异常（超时/连接拒绝）一律折算为"离线"，**消费方不得因探活失败报错中断业务**。
- 探活超时建议 3s。

### 2.2 向量化：`POST /v1/embeddings`（OpenAI 兼容）
- 请求体：`{"input": ["text1", "text2", ...], "model": "qwen3-emb"}`
- 响应：`data[].embedding`（float 数组），**按 `data[].index` 排序后使用**（服务端当前版本实测保序，但契约层面不依赖保序——记忆侧待对齐项①，见 §7）。
- **维度**：当前家族统一 **1024 维**（EMBED_DIM=1024 已钉死于记忆侧常量与 embeddings 表结构）。**换模型 = 全量重嵌 + embeddings 表重建**，属高成本迁移，慎行——不要轻率更换嵌入模型。
- 批量：**服务端未强制上限（实测 65 条返回 200）**；建议单请求 ≤64 条作为稳定性预算（叠加单请求槽限制，贪大只增加排队与超时风险）；单请求超时建议 90s。

## 3. 边界行为（2026-10-01 三方实测定案）

| 边界 | 实测行为 | 消费方要求 |
|---|---|---|
| 空文本（空串/纯空格） | **200 + 1024 维有效向量**（非零；不同空白输入向量不同，实测 cos≈0.49） | 过滤空条目是**卫生习惯**（空向量是无意义数据），不是报错规避 |
| 超长文本 | **超 8192 token → HTTP 400**，错误体明示 `exceed_context_size_error` + `n_prompt_tokens`/`n_ctx`（实测 30k 字符≈9013 tok 触发；10k 字符≈3096 tok 正常）。**真报错，非静默截断** | 消费方按 **token 预算**（非字符数）控制单条长度——中文/代码密度不同。现行为：博物切块 1200 字符、记忆截断 600/1500 字符，均安全 |
| 偶发断连 | `WinError 10054` | **博物**：重试一次（退避 1.5s）再降级；**记忆**：无重试，一次异常直接回退纯 tag。新消费方二选一，推荐带一次重试 |
| 服务重启窗口 | 看门狗重启期间短暂离线 | **博物**：探活失败重试一次再降级；**记忆**：直接降级（与断连同路） |

> 历史注记：博物 v0.1 首批向量化时 8 个文件报 400，当时归因"空白块"——按本次实测（空文本返回 200）该归因存疑，真因未复现（疑为超长块）。若再见 400，先查 token 超限（错误体会给出 n_prompt_tokens）。

## 5. 控制面与看门狗（基建运维资产）

**归属**：控制面四操作（`embed-status` / `embed-ensure` / `embed-stop` / `embed-restart`）与看门狗属**流变·基建**（`dsh-liubian-infra`）——2026-10-01 由 dsh-liubian-embed 挂牌迁移（过渡期别名 `_dsh_external_dsh_liubian_embed` 同实现）。llama-server 有提交内存泄漏前科（实测 5.5h 涨到 10.9GB，重启回落释放 9.2GB），**任何归属变更必须完整随迁看门狗，不能裸奔**（记忆向量提醒在案）。

### 5.1 看门狗参数（2026-10-01 纠偏后）

| 项 | 值 | 说明 |
|---|---|---|
| 阈值 | **私有提交 > 12288MB** | ⚠ 旧值 **4096MB 是错的**：本机**空载稳态即 ≈10.8GB**，旧阈值永不达标 → 全天击杀 **80 次**，每次击杀都是整模 GPU 重载尖峰。这就是"**没向量任务却跑满 GPU**"的根因。**阈值必须显著高于空载稳态。** |
| 间隔 | 300s | |
| 防抖 | **连续 2 轮超限**才动手 | 300s×2 = 需持续超限 10 分钟 |
| 避让 | 8082 有活动连接则**顺延** | 不在批量向量化进行到一半时杀 |
| 测量 | `privateCommitMb(pid)` | ⚠ 收 **PID**；传映像名会**静默返回 0**，症状与"测量失效"一模一样 |

### 5.2 两个停止入口的语义差异（**必须分清，否则会以为"看门狗乱动我的进程"**）

| 你做的事 | 语义 | 看门狗行为 |
|---|---|---|
| `embed-stop`（控制面） | **显式停止**：置 `explicitStop` 标记 | **不抢**——保持关着（省显存就这么做） |
| 直接 kill 进程 / 崩溃 | **异常死亡** | **自动恢复**（v0.4.0 存活恢复） |

**2026-10-01 当晚事故**（本表的由来）：llama-server 静默死亡 **≥90 分钟**（≥21:04 → 22:35），消费方 error.log 三次 `嵌入请求失败（fetch failed）`（21:04 / 21:57 / 22:24），而**没有任何日志记录它是怎么死的**。根因＝旧看门狗**只管"内存超限"、不管"进程还在不在"**（探活失败即 `return`），进程一崩就再没人拉起，直到下次 DSH 重启。已修：存活恢复判据（纯函数 + 桩测）+ `explicitStop` 标记防抢 + 拉起结果按 `launch()` **实际返回值**记账 + 3s 存活复查。

### 5.3 其它运维约定

- **ensure 防重复拉起**：冷却 180s + spawn 前先查存活进程（进程在、哪怕还在载入模型 → 不许再拉一个）。旧版无冷却曾被每分钟触发 → 一天 18 个实例抢 8082，每个都是整模载入。
- **启动方式**：直起 exe + **`windowsHide:true`**；**`detached` 必须为 false**（`true` 会被 Node 升级成 `CREATE_NEW_CONSOLE`，冒黑框）；别走 `cmd/start`（同样新建控制台）。**完整参数以 §1「启动参数要点」与 `infra-plugin` DEFAULTS 的 `serverArgs` 为准——含 `-m <模型>`，漏了它只会得到一个 400 空服务。** 输出落盘到 `~/.dsh/liubian-infra/llama-server.log`（`serverLogFile`，v0.4.0 起）。沿革与观测方法见 `infra-plugin` 源码注释与交接书 §5。
- **看门狗随迁条款**：本表数值是运维资产的一部分，改归属/改实现必须整表随迁。
