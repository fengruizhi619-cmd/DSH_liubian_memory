## 3. 注册半场（管理员已钉定义，契约先行 + 消费者登记表）

**管理员定义（06:08 原文要点）**：独特名服务于四个**即将到来**的功能——
1. **便签系统**（即将到来）
2. **记忆系统新改版的贡献者功能**
3. **被炉未来的 p2p 功能**
4. **留言板**（旧记忆系统中与记忆读取/日记写入/校验〔今孪生〕并列的功能，被炉之后实现）

即：独特名 = **跨插件的参与者身份名**，四个消费功能全部在未来时。

**现状盘点**（孪生）：两套各自工作的局部机制——
- 被炉昵称唯一：房间内作用域（同昵称可跨房间），重名自动后缀、最终名回传；房间 ID = 会话号哈希前 8 位防碰撞
- tag 规范名 + 别名表：记忆内部已实现（1.6 万 tag 规范名体系在跑）

**按孪生判据的现状**：现有消费者 = 0（四个功能均未落地）——契约先行结论反而更稳：不为零个现有消费者建服务，但骨架现在立。

**触发条件**（满足其一即重启基建评估）：
1. 四个功能中任一真正开工（首个消费者的实现就是注册语义的第一次试错）
2. 注册语义扩展到需要跨插件一致的凭据/权限
3. 孪生判据：消费者 ≥3 且各自都在重写一遍调用逻辑

**关键技术待决**（契约骨架必须先回答）：作用域语义——四个功能里的独特名是**全局唯一**（同一参与者在便签/贡献者/p2p/留言板共用一名）还是**分域唯一**？管理员定义暗示前者（"这些功能都依靠于独特名"= 同一名贯通多系统），但需明文钉死。次要待决：独特名的属性集（花名？短 ID？凭据/密钥？与既有 30 花名用户体系的关系？）。
