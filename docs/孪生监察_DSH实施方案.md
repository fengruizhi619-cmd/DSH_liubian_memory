# 孪生监察（执行 + 监察双智能体）DSH 实施方案 v3

> 状态：**待审查，未实现**。本文件只描述方案，批准后才动代码。
> v1 → v2：拦截从"注入建议"升级为真闸门（工具闸门源码级确认可 deny）。
> v2 → v3：**找到两个时点的"征兆"** —— 输出流的 `tool-call-delta` / `text-delta`；
> 并确认宿主把整个模型输出流开了个可包裹的口子（`llm/stream` waterfall，文档原话
> "possibly wrapped by `llm/stream` listeners"）。文本闸门因此可以做到**真·显示前拦截**。

---

## 0. 一句话

同一个会话里放两个智能体：执行干活，监察在**两个闸门**上审它是否偏离用户指令。
通过就放行，偏离就把纠正送进执行的上下文（工具闸门时执行的动作**不会发生**）。

---

## 1. 两个闸门（本方案的核心，含源码级证据）

### 1.1 闸门一：准备调用工具时（硬闸门，真拦截）

**机制**：宿主在工具执行前跑一个 waterfall ——
`const gate = await this.ctx.waterfall(carrier, "tools/pre-execute", exec, () => Promise.resolve({ kind: "allow" }))`。

- 默认 `{kind:'allow'}`；可返回 `{kind:'ask'}`（走宿主审批流程）或 `{kind:'deny', reason}`。
- 拿到 decision 后宿主做：`const denialReason = decision.kind === "allow" ? this.guardReason(exec) : decision.reason;`
  若有 reason，则**短路**成：
  `materializeFinalResult({ content: [{ type: 'text', text: \`Error: ${denialReason}\` }], isError: true })`。
- 也就是说：**返回 deny 后工具根本不执行**，我们的纠正文本以工具错误的形式回给执行智能体，它必须据此改。
- waterfall 是 await 的 → **可以在闸门里同步等一次监察调用**。

**结论**：用户要的"停止执行 → 送监察 → 通过放行 / 有问题纠正"在工具这个时点是**完全可实现**的。

### 1.2 闸门二：准备输出文本给用户时（**征兆已找到**）

#### 征兆：流的 `text-delta`

宿主把模型输出做成一条分块流，分块类型实测为：
`reasoning-delta` / `text-delta` / `tool-call-delta` / `block-end` / `finish`（另有组装后的 `text` / `reasoning` / `tool-call`）。
组装逻辑（宿主源码）：

```js
case "text-delta":        partial.text += chunk.text;                       // → {type:'text', text}
case "reasoning-delta":   partial.text += chunk.text;                       // → {type:'reasoning', text}
case "tool-call-delta":   partial.toolCallId = chunk.id;
                          if (chunk.name) partial.toolCallName = chunk.name; // 工具名先到
                          partial.toolCallArguments += chunk.argumentsDelta; // 参数陆续累加
                                                                             // → {type:'tool-call', id, name, arguments}
```

于是两个"征兆"都是**结构性、可精确判定**的：

| 时点 | 征兆 | 出现时机 |
|---|---|---|
| 准备调用工具 | 流里第一个 `tool-call-delta` | 工具名已到（`chunk.name`），参数尚未拼完 → 比"组装完成"更早 |
| 准备输出给用户 | 流里第一个 `text-delta` | `reasoning-delta` 不算（那是思考，不是输出给用户） |

#### 拦截点：`llm/stream` 是一个可包裹的 waterfall（宿主原话）

```js
streamWithRegistration(options, prepared) {
    return this.ctx.waterfall(this, "llm/stream", options, () => this.adapterStream(options, prepared));
}
```
> 文档注释：「The abstract `llm` service: an adapter registry plus a streaming model-call API,
> **interceptable via the `llm/stream` waterfall**」；返回值：「the chunk stream,
> **possibly wrapped by `llm/stream` listeners**」。

即：插件可以 `const stream = await next(options)` 拿到原始流，再**用自己的 async generator 包一层**，
逐块检查、决定放行 / 扣住 / 改写 / 替换。

注意区分（这决定了两个闸门为什么做法不同）：

- **工具时点**：不需要动流。让流正常过去，宿主组装后必然走 `tools/pre-execute`（§1.1），
  在那里 deny 即可 —— 用的是宿主正式闸门，**不碰热路径**。
- **文本时点**：**必须**动流。因为宿主没有"输出前审一遍"的原生闸门 ——
  `this.dispatch.emit("agent/assistant-stream", { frame })` 是 **emit（纯通知）**，拦不住已流出的文本。
  要"显示前拦下"，只有 `llm/stream` 包裹这一条路。

#### 文本闸门的两种形态（★ 已定：只能用 B）

**硬要求（用户明确）**：一旦命中需审查的节点，**必须把执行的对话停下来**，等审查完才允许继续；
**绝对不允许「边审查边输出」**。原因：长时间调用工具一般是训练这类任务，时间成本高，且几乎不允许方向性错误——
边审边跑在这种场景下极容易出事。

- **形态 B · 流包裹（唯一满足要求的形态，采用）**
  在 `llm/stream` 里包一层：`reasoning-delta` 立刻放行（用户仍能看到思考在流）；
  **`text-delta` 全部扣住不放** → 流被挂住 → 该 step 不结束、执行彻底停住（UI 停在「生成中」，不吐出任何未审内容）；
  等 `finish` 拿到全文 → **同步**送监察 → 审完才决定放行或替换。
  - 通过 → 把扣住的原文按序放行 + 放 `finish`。
  - 不通过 → **不放原文**；改为放一条短提示 + 一个**合成的 `tool-call-delta`** 指向本插件注册的
    `_twin_note` 工具 → 宿主执行它、把纠正作为工具结果回给模型 → 回合继续、模型重写。
  **代价**：答案不逐字流式（「思考流 → 停顿 → 整段出现」）；且这是**每次模型调用的必经热路径**（见 §10）。

- **形态 A · 回合内强制纠正（⚠️ 已否决）**
  `agent/turn-stopping` + `agent.inject` 逼迫重写。**它不满足「停下等审查」**——文本已经流出去，
  等价于边审边输出，故仅作为 B 被关掉或异常时的降级兜底，不作正常路径。

#### 停等语义（stop-the-world）

两个闸门都必须是**阻塞式**的：审查期间执行侧零产出。

| 闸门 | 停住的是什么 | 为什么天然阻塞 |
|---|---|---|
| 工具闸门 | 工具**还没执行**（`tools/pre-execute` 在派发前裁决） | 返回 deny 前工具不动 |
| 文本闸门 | 文本分块**被扣住**，step 不结束 | 流不推进 → 执行不产出、UI 停在生成中 |

三条必须实现的纪律：

1. **同步等审查**：监察调用必须 await；不允许「先放行、异步补审」。
2. **期间零输出**：不得为显示进度而放行部分文本；用户看到的就是「停住」（UI 本就在生成态）。
3. **中断优先**：用户按停止 → `signal` 中止 → 必须立即释放已扣住的分块并透传/丢弃，绝不让流悬挂。

#### 失败与重试策略（★ 已定，用户指定）

**重试**：监察调用失败（传输错误 / 超时 / 裁决无法解析）→ **每 5 秒重试一次，共 5 次**。
5 次（约 25 秒）仍失败 → 按下面各自的收尾动作终止，绝不再无限等待。

**工具闸门 5 次全失败 → 逐条拒掉 + 固定文本 + 排队中断回合**（★ 2026-09-18 实测事故后修正）

> **为什么不再是"先送 notice 再 cancel"**：工具闸门被调用的时刻，正处在
> 「assistant 带 `tool_calls` 的消息已经落盘、它的工具结果还没落盘」这个窗口里。
> 此刻 `session.append` 一条 notice，线格式就变成
> `assistant(tool_calls) → user(notice) → tool(result)`，上游从下一个回合起**每个请求都 400**：
> `An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'.
> (insufficient tool messages following tool_calls message)`
> —— 这条会话**永久作废**（实测 session-ea61564d：22:42 起再也发不出请求，只能弃用）。
> 同一次事故还暴露第二个坑：送监请求的尾巴同样是那条未回填的 `assistant(tool_calls)`，
> 上游直接拒收（108ms 返回、流里一个字节都没有 = "空回复"）→ 5 次重试全废，**工具闸门等于从未生效**。
>
> **纪律**：工具窗口里只许返回 deny；**一个字节都不许写会话，也不许中断回合**。
> 所有写入（监察记录 / 固定文本 / 中断）一律排队，等 `step/end`（工具结果全部落盘）再执行。

1. 固定文本与中断动作**排队**（`st.pending`），并给本回合打上 `twinDown`：
   本步剩下的工具调用一律直接 deny（不再重试、不再等），固定文本先让模型从工具结果里看到。
2. 到 `step/end` 再落盘：notice 走 `user/message` + `form:'notice'`（形状照 `dsh-repeat-tool-reminder`，
   那是"notice 长什么样"的先例），随后 `agent.cancel(cause, { keepInbox: true })` 中断回合。
3. 闸门自身始终返回 `{kind:'deny', reason:'监察api不可用…'}` 作保险：
   该次工具调用在任何时序下都不会执行，而那行 `Error: 监察api不可用…` 就是用户看到的那句固定文本。
4. 送监请求必须先过 `sanitizeForTwin()`：给尚未执行的调用补一条占位工具结果，
   否则请求形态非法、上游拒收（表现为"空回复"）。

**文本闸门 5 次全失败 → 放行原文 + 末尾补一句申明**：

1. 把扣住的文本分块**原样放行**（模型的话照常输出，不因监察故障而扣死）。
2. 在末尾补一句申明（同一句固定文本）。
   实现要点：本插件的流包装器要在 `try/finally` 里做这件事——
   消费方在收到 `finish` 后会 `break` 跳出 `for await`，**`finish` 之后的代码不保证执行**，
   所以申明必须在 `finish` 之前落地（或放进 `finally`）。

固定文本与重试参数全部可配：`twinUnavailableText` / `twinRetryDelayMs`（5000）/ `twinRetryMax`（5）。

### 1.3 两个闸门统一放行/拒绝的形态

每次审查结束后（无论通过与否）都**追加一条助手消息承载监察思考**（见 §3.5，原生渲染）；
判为偏离时，在追加之外再走原来的注入通道发纠正。

| 时点 | 通过 | 有问题 | 监察故障（5 次重试后） |
|---|---|---|---|
| 工具闸门 | 返回 `{kind:'allow'}`，工具照常执行 | 返回 `{kind:'deny', reason:'[监察] …纠正…'}` → 工具不执行，执行收到 `Error: [监察] …`，被迫改；同时注入 `<twin-review>` 纠正 | 逐条 deny + 工具结果里带固定文本；notice 与 `agent.cancel` 排队到 `step/end` 落盘 |
| 文本闸门 B | 放行扣住的原文 + `finish` | 不放原文；短提示 + 合成 `tool-call-delta` 指向 `_twin_note` → 模型重写 | 放行原文 + 末尾补一句固定文本申明 |

两条闸门的**写入时机**都受同一条纪律约束：只有当会话不在"工具窗口"里（即 `assistant(tool_calls)`
后面已经跟齐了它的 tool 结果）才允许落盘；因此监察记录一律排队，在 `step/end` / `step/start` 落。

两条通道的分工：**追加的助手消息＝显示与记录**（监察思考 + 裁决，原生渲染）；
**注入的纠正＝给执行的指令**（user 角色插件消息，执行会当外部指令照做，比"自己说过的话"更有效）。

## 2. 成本（实测数据决定默认策略）

### 2.1 实测：工具调用的"连续"程度（8 个真实会话、2946 次工具调用）

| 口径 | 数量 | 占工具调用 |
|---|---|---|
| 工具调用总数 | 2946 | 100% |
| 含调用的步数（按步审的闸门机会） | 2608 | — |
| 同一步内 ≥2 次调用（并行批量） | 626 | **21.2%** |
| 位于"连续步调用链"内（串行连续） | 2944 | **99.9%** |
| 调用链条数 | 107 | 链 ≈ 一个回合内的连续工作序列 |

- 每步调用数分布：1 次 2320 步、2 次 252、3 次 25、4 次 8、5 次 3 → **平均每步仅 1.13 次**。
- 链长分布：2 ~ 33+，长 19/25/27/33 各有多条。
- 单会话规模差异极大：最小 73 次调用/49 步；最大 **2211 次调用/2157 条模型消息**。

### 2.2 由此得出的三条结论

1. **"按次审"与"按步审"几乎等价**（2946 vs 2608，仅省 11%）——因为每步平均 1.13 次调用。
   这一点省不出成本，不必在这上面设计。
2. **真正能省的粒度是"按链"**：107 次 vs 2946 次（省 96%），但代价是链内不再逐动作审，
   而链可长到 33 步——链首方向正确 ≠ 链尾没跑偏。所以单靠按链审会丢掉"审最新动作"的粒度。
3. **全审在数学上出局**：最大会话 2211 次调用。预算抽样是**必需项**，不是优化项。

### 2.3 闸门触发规则（用户定义，已用实测数据模拟验证）

**规则**：

1. 该动作**前面不是同类动作**（前面不是工具调用 / 前面不是文本输出）→ **必审**（即链首必审、每个回合的首次输出必审）。
2. 该动作前面**是同类动作**（链内）→ 看**距上一次审查**的间隔：
   - 间隔 **≥ `twinGapCalls`（默认 10）次动作** → 触发审查；
   - 或间隔 **≥ `twinGapMinutes`（默认 10）分钟** → 触发审查；
   - 两者都不满足 → 跳过。
3. 输出同理。

> 口径说明：「间隔」按**距上一次审查**计。若按字面理解为"距上一次工具调用"，链内恒为 1、
> 永不触发，退化成"只审链首"（实测总量约 216 次）。

**两条阈值的意义＝及时止损（用户定性）**：它们的共同目的不是"每次都审"，而是**不让错误方向
无人过问地跑太久**——无论按次数还是按时间，哪个先到就审一次，把损失窗口封在有限范围内。

**为什么不需要识别"训练任务"（用户给出的理由，已接受）**：训练这类长任务在链里的位置只有两种——
要么**它就是链首**（直接开跑），要么**它前面必然有写代码/改配置的工具调用**。
而链首必审、链内每 ≥10 次或 ≥10 分钟必审一次，所以**总有一个检查点会盖到它**。
因此**不做任何按工具类型的过滤或分类**：所有工具一视同仁，也没有"重量级调用分类器"。

> 实测支持这个判断：调用链共 108 条、链首全审（108 次），链长中位数很高（19/25/27/33 各有多条），
> 即"一条工作序列的开头必有一次方向审查"，正是该论证依赖的前提。

> ⚠️ 但要如实说清止损的边界：这是"**有界**"，不是"**每次动作都拦住**"。
> ①训练若不是恰好落在检查点上，它自己那一次调用不会被审（靠链首/上一次检查点判方向）；
> ②更硬的一条：**长时间工具调用在执行期间不可能被检查点打断**——该调用跑着时执行侧被占住，
> 下一个检查点要等它返回才发生。所以一个方向错误的长任务的止损点，最早是它**返回之后**的第一次审查。
> 若要在长任务跑到一半就掐掉，需要另加"定时看门狗 + 用 `exec.signal` 中止在飞调用"这个机制
> （与分类器无关，是独立的可选增强；默认不做，你需要就说）。

**实测模拟结果（同一批 8 个会话）**：

| 指标 | 数值 |
|---|---|
| 工具调用总数 | 2952 |
| 文本输出总数 | 136 |
| 调用链条数（≈ 回合数） | 108 |
| **审查总次数** | **468**（工具 354 + 文本 114） |
| ├ 链首 / 首次输出触发 | 216 |
| ├ 「次数间隔 ≥10」触发 | 246 |
| └ 「时间间隔 ≥10min」触发 | **6** |
| 工具调用被审覆盖率 | **12.0%** |
| 相比逐次全审节省 | **88%**（2952 → 354） |
| 折合每回合审查次数 | **≈ 4.3 次**（大会话 62 链 / 315 次 ≈ 5.1） |

**观察**：①"时间间隔"这条（8 会话仅 6 次触发）抓的是"重量级/慢操作正在进行"这个状态，
按用户给的理由必须保留；②真正要防的不是"单点误拦"，而是"闸门把回合拖死"——
每回合约 4 次审查、且是**阻塞式**（审查期间执行完全停住），所以预算上限与失败时的取向（§1.2 末）是关键防线。

### 2.4 单次审查的增量成本

监察请求 = **整份会话上下文（与执行请求逐字节相同 → 命中前缀缓存）+ 末尾一条监察指令**。因此：

- **新增 token ≈ 监察指令本身**：判据 `criteria.json` 渲染后 ≈2.6k 字符（44 条）
  + 角色/用法/契约/指认文字 ≈0.6k → 整条指令 ≈3.2k 字符（约 **3k tokens**）/次。
- **复用的上下文走缓存价**（DeepSeek 端点有 `prompt_cache_hit_tokens`），不按全价计。
- 另有监察自身输出的 token（裁决 JSON，通常几十~几百 tokens）。
- 与"每回合约 3 次审查"（§2.5 实现后复算）相乘，可得每回合增量量级。

并与 `_recovery/gate_policy_sim.cjs` 的参照算法在同一批动作上对账：

**逐条一致**，规则实现没有跑偏（会话样本按 mtime 取，与 §2.3 的 2952/468 不是同一批，故绝对值不同、量级一致）。

**逐回合看（真实姿态：回合重置 + 预算上限）**：162 个有动作的回合、498 次审查、工具覆盖率 10.6%、
每回合 3.07 次；但**单回合候选数中位 9、最大 72，162 个回合里有 82 个超过 8**——
按原定 `twinMaxReviewsPerTurn: 8` 会拦掉 550 次（占候选一半），预算就从"兜底"变成了"主要限流器"。
故默认值抬到 **12**（仍能拦住 72 那类巨回合），见 §7。

## 3. 送监格式：**照抄 DSH 自己的请求格式**（不手搓）

### 3.1 DSH 组装请求的真实形状（源码）

```js
return markAgentLoopRequest(Object.freeze({
    ...header.config,                        // provider / model / reasoningEffort / temperature / maxTokens / stop
    messages: session.deriveMessages(),      // ← 会话推导出的消息数组
    ...(header.tools !== void 0 ? { tools: header.tools } : {}),
    sessionId: this.session.id,
    signal
}));
// 实际调用：preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)
```

`deriveMessages()` 是 `dsh-session` 的方法，把会话事件逐条经 `deriveEventMessage(event)` 投影成消息。
**消息数组不是插件拼的，是会话推出来的。**

### 3.2 监察请求 = 同样的形状，只在末尾追加一条指令

```js
messages = [
  ...agent.session.deriveMessages(),          // 原样复用（未改动，deepFreeze 过，需拷新数组）
  监察指令消息,                                // role:'user'，source:{kind:'plugin', plugin:'dsh-liubian-twin'}
]
ctx.llm.stream({ provider, model, messages, signal })   // provider/model 取自 session.requestContext()
```

监察指令消息（追加在末尾）包含：

1. **监察角色与硬要求**：取自 `criteria.json` 的 `role`（正向措辞，见 §3.8）。
2. **判据**：取自 `criteria.json` 的 `items`（平铺条目，一条判据一条，各自带 `when` 使用场景；正向、可执行、不写来源）；
   连同 `usage` 一起给出——"下面每一条都是用来检查被审动作的，按 `when` 对场景取用"。
3. **输出契约**：取自 `criteria.json` 的 `contract` —— 只输出 JSON `{"conform":bool,"reason":"…","correction":"…"}`。
4. **指认待审对象**：本回合第 N 步的哪个动作（工具调用 / 文本输出），
   并指明"用户原始指令见上文最后一条 user 消息"。
5. **请求里带 `tools` 的选项留空**：监察只回 JSON。

> 注意：**不再装载任何技能文件**（§3.8）——判据全部来自 `criteria.json`。

### 3.3 为什么这样做（比手搓格式强在哪）

- **同源问题自动消失**：接入卡 / 教训块 / 能力卡 / 逐轮提醒本来就作为 user 角色插件消息活在会话里，
  `deriveMessages()` 直接带上它们 → 监察看到的与执行看到的**必然一致**，
  不存在"两份构造器漂移且不报错"的风险（v1 里为此专门论证过要合进 liubian 复用构造器，现在连复用都不需要了）。
- **吃到前缀缓存**：监察请求的前段与执行上一次请求逐字节相同，只有末尾追加的指令是新 token。
  反之若把监察角色做成 system 消息放最前，第一个 token 就分叉，前缀缓存全废。
- **真孪生**：provider/model 直接取 `session.requestContext()`，就是执行正在用的模型，无需额外配置。
- **线格式零重写**：role、content parts、tool_calls、reasoning 的序列化全部由宿主的 llm 适配器负责。

### 3.4 可见性与"思考"的命名（用户指定）

**命名**：执行智能体的思考＝**执行思考**；监察智能体的思考＝**监察思考**。

**可见性矩阵**（用户最终口径）：

| 内容 | 执行智能体可见 | 监察智能体可见 | 用户可见 |
|---|---|---|---|
| 用户信息（原始指令） | ✓ | ✓ | ✓ |
| 执行思考 | ✓ | ✓ | ✓（DSH 原生渲染） |
| 执行的动作（工具调用） | ✓ | ✓ | ✓ |
| 执行的输出 | ✓ | ✓ | ✓ |
| **监察思考** | **✓**（用户明确：让执行看到也无所谓） | ✓（自己的历次思考都带上） | ✓（原生渲染） |
| 监察的输出（裁决／纠正） | ✓ | ✓ | ✓ |

> v3 早期版本要求"监察思考对执行不可见"，那会把显示逼到客户端 UI 里做。
> 用户后来放开这条（"让执行模型看到也无所谓，反正按照原生渲染即可"），
> 于是**显示可以直接用 DSH 原生渲染，整块客户端 UI 工程取消**。

**实现含义**：

- 监察思考与裁决**都作为一条助手消息追加进会话**（见 §3.5），因此执行与用户都能看到；
- 监察侧在自己的请求里除 `deriveMessages()` 外，还追加**本会话历次监察思考与输出**
  （由本插件按 session 维护，内存 + `~/.dsh/liubian-twin/sessions/<sessionId>.jsonl`），
  这样它跨多次审查有连续性——这是"额外包含自己的思考过程和自己的输出"的落地方式。

### 3.5 监察思考的插入形式：**用原生渲染**（不用客户端 UI）

**原生思考行是怎么渲染的**（`@deepseek-ai/dsh-client-ui-chat` 的 `ReasoningRow`，源码级）：

```js
function ReasoningRow({ text, running, t }) {   // "Assistant reasoning disclosure"
  const [expanded, setExpanded] = useState(false)
  const summary = (running ? latestLine(text) : firstLine(text)).replaceAll('**', '')
  return <div data-variant="think" data-state={running ? 'running' : 'ok'} data-expanded={expanded || undefined}>…</div>
}
```

- 由消息 content 里的 `reasoning` 块驱动：`case "reasoning": → <ReasoningRow text={block.text} running={streaming && i===last}/>`；
- 折叠态占一行（高 `24px + 字体增量`），显示**单行摘要**：**生成中取最后一行、结束后取第一行**（去 `**`）；
- 展开看**完整正文**（`pre-wrap`）；`running` 时有 300px 扫光（2.6s 循环）；
- 归在"过程"区（`ProcessReasoning` 的 `hidden` / `reveal` 控制）。

**所以我们只要把监察思考放进一条助手消息的 `reasoning` 块，原生渲染就白拿**：

```js
// 每次审查结束后追加（createAssistantMessage：source 默认 {kind:'model'}，可覆盖）
agent.session.append('assistant/message', {
    turn, step,
    message: createAssistantMessage({
        content: [
            { type: 'reasoning', text: 监察思考全文 },
            { type: 'text',      text: `〔监察〕${conform ? '通过' : '纠正'}：${reason || correction}` },
        ],
        source: { kind: 'model', provider, model },   // 或 {kind:'plugin', plugin:'dsh-liubian', form:'notice', summary}
    }),
}, { surfaceOp: 'append' })
```

执行思考仍由 DSH 原生渲染（消息里既有的 `reasoning` 块），我们不动。

**已知取舍（用户已接受）**：这条助手消息对执行**可见**，所以执行会在下一轮看到"自己"的思考里夹着监察思考；
文案上会带 `〔监察〕` 前缀以便区分。若哪天要改回"执行不可见"，只能回到客户端 UI 方案（§3.6 记录了那条路的全部结论）。

### 3.6 备选（已搁置）：客户端 UI 路线

若日后重新要求"监察思考对执行不可见"，则必须走客户端 UI，因为：

| 事件类型 | 进模型上下文 | 进人类对话记录 |
|---|---|---|
| `append` 型表面事件 | ✓ | ✓ |
| `replacement` 型表面事件 | ✓ | ✗（源码注释："replacement copies **stay model-only**"） |
| 非表面事件（log-only） | ✗ | ✗ |

**没有"用户可见 + 模型不可见"的组合**（`notice` 是 user/message → 模型可见）。
届时做法：`exports["./client"]` + `dsh.client{platform:'web',immediately:true,inject:[...]}`（照抄本机
`dsh-progress-target`）+ `ctx.slots.inject('conversation.view', () => ctx.slots.register({name,id,order,label}, TwinPanel))`
+ 只读路由取数；可用槽位实测有 `conversation.view`、`conversation.session.header`、
`conversation.composer.dock`、`conversation.composer.bar`、`conversation.input.dock`、
`conversation.chat.node`（按 kind 键控，行内）。


### 3.7 实现要点与坑

1. **递归防护（必须）**：监察自己的调用也会流经 `llm/stream`，而形态 B 的闸门正挂在那里 →
   必须给自己的请求打标记并在闸门里跳过。宿主自带 `markAgentLoopRequest` 先例，说明打标是常规做法。
2. `deriveMessages()` 返回的消息已被 `deepFreeze` → 追加时**必须拷新数组**（`[...derived, mine]`）。
3. 插件需把 `llm` 加入 `inject`（现为 `['tools']`）才能取到该服务。
4. **上下文规模**：默认全量复用 derived 消息（这才是"同源 + 缓存"的关键）。
   若实测发现监察被无关历史干扰或成本过高，再退化为"裁剪切片"，但那会失去逐字节相同的前缀。

### 3.8 监察判据：**插件独属的一个 JSON，按审查者口吻专门重写**（用户决定）

**不装载任何技能文件。** 理由（用户给出的，且与实测一致）：

1. 技能文件带的是**给执行者的触发条件**——frontmatter 的 `name` / `description` / when-to-use
   是给模型判断"要不要加载这个技能"用的，监察既不做这个判断，这部分就是纯噪声；
2. 技能正文是**执行者口吻**（"做任何事情都要先依次自问七问，再动手或给结论"），
   而监察是**审查者**——主体从"我"变成"我在审的那个动作"，照搬会产生视角错位
   （本机教训 D0147：监察很可能把七问当成自己的作业答一遍，产出与审查无关的东西）；
3. 技能里大量内容是**做法**（怎么写、怎么一步步做），监察要的是**判据**（这算不算做错）。

**所以判据单独成文，封成插件独属的 JSON**，随插件分发：

```
C:\Users\Feng\.dsh\plugins\dsh-liubian-twin\criteria.json      # 插件自带默认（版本受控、随插件走）
~/.dsh/liubian-twin/criteria.json                              # 可选：用户覆盖（存在则优先，便于调措辞）
```

配置项：`twinCriteria: ''`（空 = 用插件自带那份；填路径 = 用覆盖那份）。
**不再有 `twinSkills`**（已删）。

#### 判据 JSON 的结构（一条判据 = 一个条目，条目自带使用场景）

```json
{
  "version": 1,
  "role": "（监察角色与硬要求，见下）",
  "contract": "只输出 JSON：{\"conform\":bool,\"reason\":\"…\",\"correction\":\"…\"}",
  "usage": "（一句话说明这些条目怎么用，见下）",
  "items": [
    { "id": 1, "when": "什么时候查这一条", "q": "要检查什么" }
  ]
}
```

**一条判据一个条目，各自带 `when`（什么时候查这一条）。** 不按来源技能分组：
技能只说明这条判据是从哪儿抄来的，不说明它什么时候该用。监察拿 `when` 对场景，
对得上就查，对不上就跳过。**判据里不写来源**——来源对监察没用，
它只需要知道"什么场景下查什么"（用户指定）。

#### 写法要求（用户指定）

用最普通的话写清楚，一读就知道要查什么：不用比喻，不用行话，
不写"抽象层""脚手架"这类还要再解释一遍的词。每条一律写成**要求做某事**，不写成禁止某事——
禁止的写法要先做一次取反，而且会把被禁的行为一起带进上下文。

拼进请求时每条渲染成一行：

```
[场景] {when} → 要求 {q}
```

#### 草案内容（待你审阅措辞，编号可直接引用）

**role**（监察角色与硬要求）

你是监察智能体，只做一件事：审执行智能体的**最新一个动作**（思考／工具调用／准备输出的话）
是否符合用户指令，并在偏离时给出可直接执行的纠正。

1. 每条意见都要带上证据：引用被审动作里的原文、参数、数据或文件名。
2. 只报真的会导致偏离的问题；没有偏离时给 `conform=true` 加一句理由。
3. 意见里写用户还不知道的偏离点，以及下一步该做什么。
4. 判据以用户指令为准；需要改需求时，在 reason 里写明"这属于改需求"，交由用户决定。
5. 只输出 JSON：`{"conform":bool,"reason":"…","correction":"…"}`。
6. 下面每一条都只针对被审的那一个动作：`when` 对得上的逐条对照，对不上的跳过，对照完直接给结论。

**items**（44 条；`when` = 什么时候查这一条，`q` = 要检查什么）

1. 要求这一步能说出它对应的是用户说过的哪句话；说不出来的算偏离，并要求写明该做什么。
   什么时候查：每一步。
2. 要求只做用户要求的那部分；多做的部分要求撤回。
   什么时候查：动作里多了用户没要求的东西（新文件、新依赖、新流程）。
3. 要求逐条核对用户这次给出的条件（指定的文件和数据、格式、数量上限、必须经过的步骤），
   被违反的把用户原话和违反的地方写进 reason。
   什么时候查：用户这条消息里给了明确条件。
4. 要求处理的就是用户问的那个问题；换成别的问题的，要求在 correction 里改回来。
   什么时候查：动作回答的不是用户问的问题。
5. 要求结论后面带上证据和推理过程；只有结论没有依据的算未完成，要求补上依据。
   什么时候查：动作给出了结论、判断，或写了"已验证"。
6. 要求这些数字、版本、引用和别人的结论都能说出是从哪里来的；说不出来的标成"待核实"，核实前先不用。
   什么时候查：动作里出现了数字、版本号、引用或别人说的结论。
7. 要求写明这个结论只在什么条件下成立。
   什么时候查：结论来自受控条件、少量样本，或只在一个环境下试过。
8. 要求先有"同样的做法在正确设置下成功过"的对照；没有对照的，要求把结论改成"还不确定"。
   什么时候查：动作准备下"失败""做不到""没用"的结论。
9. 要求先说明这些数字是按同一套方法算出来的。
   什么时候查：两个或更多的数字被放在一起比较。
10. 要求别人按同样的步骤能算出一样的结果；算不出来的要求补上复算过程。
    什么时候查：结论依赖一次计算或统计。
11. 要求写清还排除了哪些其他原因，并区分"同时出现"和"一个导致另一个"。
    什么时候查：动作在解释这个结果是怎么来的。
12. 要求先停下来交给用户确认；没确认就做的，要求马上停并说明。
    什么时候查：动作要做的是定稿方案、批量写入、删除或覆盖这类不能撤销的事。
13. 要求先向用户提问；把"先做一版看看"改成"问清楚再做"。
    什么时候查：关键信息不全，动作却要继续往下做。
14. 要求先取得用户同意；没同意的要求交回。
    什么时候查：动作碰到了用户没有交办的文件、账号或流程。
15. 要求写之前先读一遍并确认内容没变；发现已经变了的，要求停手并告诉用户。
    什么时候查：动作要写的是共享文件、别人的产物，或有人正在用的东西。
16. 要求只讲做了什么、依据是什么；对自己做法的评语放到做完之后再说。
    什么时候查：动作是准备发给用户的话。
17. 要求能说出每一项是干什么用的；说不出用途的要求删掉。
    什么时候查：动作新增了段落、字段、文件或功能。
18. 要求合并或删掉重复的部分。
    什么时候查：动作产出的内容和已有的东西职责重叠。
19. 要求写明选了什么、排除了什么、为什么。
    什么时候查：动作给出方案或技术选择。
20. 要求只留真正用到的部分，其余改成引用和摘要。
    什么时候查：动作把大段原始材料整块复制进产物或上下文。
21. 要求每次只改一个变量，其余各组的设置保持一致。
    什么时候查：动作在搭建或修改对照实验。
22. 要求一次只留一个改动，再看它的效果。
    什么时候查：动作在同一个地方同时加了好几个改动。
23. 要求先说明这个东西是否必须存在；只是为一个功能多包一层的，要求删掉。
    什么时候查：动作新建了只为包装而存在的额外代码结构（接口、基类、工厂、配置项）。
24. 要求先找仓库里已有的实现、工具和写法，能用的直接复用。
    什么时候查：动作要写新代码或新脚本。
25. 要求优先用标准库、系统自带功能和已经装好的依赖；几行代码能做完的，要求去掉新依赖。
    什么时候查：动作引入了新的依赖或新工具。
26. 要求只留这次需要的最少改动；"以后可能用得上"的部分要求删掉，等要用时再加。
    什么时候查：动作改动的范围超出了这次的需求。
27. 要求改所有调用方共用的那个地方；只在报错那一条路上补一下的，要求改成改共用的地方。
    什么时候查：动作在修一个 bug。
28. 要求保留输入检查、出错时的数据处理和安全措施，这些必须做。
    什么时候查：动作涉及外部输入、数据保存或安全检查。
29. 要求先把问题和受影响的流程完整读一遍再动手。
    什么时候查：动作是第一次改这段代码或这个系统。
30. 要求留一个能跑起来的检查（assert 或小测试）。
    什么时候查：动作写了分支、循环、解析，或涉及金额、安全判断。
31. 要求一次只回答一个问题、只改一个变量；说清这个实验为什么必须做；先查已有的结论，不重复做。
    什么时候查：动作在设计实验、消融或对照。
32. 要求给出三样：事前写好的预期、固定的随机种子与参数环境、失败时会是什么样以及结论的边界。
    什么时候查：动作在跑实验或汇报实验结果。
33. 要求等改完设计、经用户确认后再重新开始；设计定下后按设计执行。
    什么时候查：动作在实验进行中修改参数或做法。
34. 要求把结果、过程（包括代码）和关键中间文件保存下来；失败的实验也要保存。
    什么时候查：动作结束一个实验或一轮批量运行。
35. 要求换多个随机种子各跑一次，报告平均值和波动范围。

## 6. 状态、预算与防环

per-session state 新增：

- `twinReviewed` —— 已审动作标识（去重，防同一动作被多步重复看到）
- `twinBudget` —— 本回合已用审查次数
- `twinTurnKey` —— 识别新回合时重置预算
- `twinLastReviewAt` / `twinActionSeq` —— **上一次审查的位置（动作序号）与时间戳**，
  用于规则②的两个间隔判断（`twinActionSeq - twinLastReviewSeq >= twinGapCalls`
  或 `now - twinLastReviewAt >= twinGapMinutes * 60000`）
- `twinPrevKind` —— 上一个动作的类型（tool / text），用于规则①判"前面是不是同类动作"

- 预算用尽即静默跳过（不审查、不报错）。
- **未解决出口**：监察提了意见、执行改完仍被提意见 → 第二次意见照常送，但标记"未解决"并停止继续审，
  让回合正常走完。**绝不为了纠偏卡死一轮。**
- 两个闸门与监察调用全部包 `try/catch`，异常（超时/解析失败/API 错）按 §1.2 末定的取向处理
  （工具闸门倾向 fail-closed：宁可停住，也不放行一个不可逆的重操作；文本闸门倾向 fail-open）。
- 审查期间**执行侧零产出**（§1.2 停等语义）：不放行部分文本、不让工具先行。

## 8. 代码落点：**独立插件 `dsh-liubian-twin`（流变·孪生）**

**定调（用户决定）**：这个功能**不直接属于流变系统**——功能上**不互通**（不引 `dsh-liubian` 的任何代码、
不读它的任何数据/配置），只在**命名**上归入流变系列（`dsh-liubian` / `dsh-liubian-embed` / `dsh-liubian-twin`）。

这不是妥协，反而更干净：v1 曾论证"必须合进流变，因为监察的固定提示词要与执行同源、两份构造器会漂移"，
但改用 `deriveMessages()` 之后**那个理由已经消失**——接入卡 / 教训块 / 能力卡 / 逐轮提醒本来就作为会话里的
消息存在，监察原样拿到，**不需要复用流变任何函数**。所以独立插件没有耦合代价，还多三个好处：

- **爆炸半径独立**：孪生出问题（把每轮拖慢、误拦、误中断）时停用/卸载它即可，**记忆注入不受影响**；
  （"没有独立开关"的成本因此被抵消掉大半——§10 第 8 条据此改写）
- 自己的目录、自己的配置与数据（`~/.dsh/liubian-twin/`），不挤进 `impl.mjs`（现约 2900 行）；
- 可单独发布/回滚，版本节奏与记忆插件解耦。

**插件骨架**：

```
C:\Users\Feng\.dsh\plugins\dsh-liubian-twin\
    package.json          // name: dsh-liubian-twin；dsh.bundle.patch: ./cordis.patch.yml
    cordis.patch.yml      // - insert: - { id: dsh-liubian-twin, name: dsh-liubian-twin }
    lib/main.mjs          // 入口壳：export name / inject=[ 'tools', 'llm' ]；带时间戳动态 import impl.mjs
    lib/impl.mjs          // 全部实现（闸门 + 监察核心 + 落盘）
```

**为什么 `inject` 需要这两项**：

- `llm` —— 监察调用走宿主的 `ctx.llm.stream()`（§3.1，线格式与模型都由宿主决定）；
- `tools` —— 文本闸门被拒时要合成一个 `_twin_note` 工具调用（用其结果把纠正回给模型），该工具要注册。

**判据读取**：**不装载任何技能文件**（§3.8）。判据来自插件自带的 `criteria.json`
（用户覆盖放 `~/.dsh/liubian-twin/criteria.json`，配置 `twinCriteria` 可指到别处）。
技能是给执行者看的（触发条件 + 做法 + 执行者口吻），监察要的是判据，视角不对，所以专门重写。

**配置与数据（全在孪生自己目录）**：

- 配置：`~/.dsh/liubian-twin/config.json`
- 监察思考记录：`~/.dsh/liubian-twin/sessions/<sessionId>.jsonl`

**没有独立开关**（§7）：孪生随**本插件**启用/停用——这正是独立插件带来的好处（不必为它单设开关）。

## 10. 已知限制与风险

1. **形态 A 已否决**（文本先流出＝边审边输出，违反硬要求）；只有 B（`llm/stream` 包裹 + `text-delta` 扣住）
   满足"停下等审查"。代价是 B 是热路径改造，见下条。
2. **★ 热路径风险（本方案最大风险）**：`llm/stream` 是每次模型调用的必经之路（实测一个会话 49 次调用）。
   包裹层必须绝对防御：
   - 任何异常 → 立刻原样放行剩余分块，绝不吞掉模型输出；
   - 尊重 `signal`：一旦中止，立即释放已扣住的分块并透传/丢弃；
   - 只碰 `text-delta` / `text`，其余分块（`tool-call-delta`、`reasoning-delta`、`finish`）一律直通；
   - 扣住时长受 `twinTimeoutMs` + 重试上限（5s × 5 次）限制，到点按 §1.2 的失败策略收尾，
     绝不无限等待。
3. **合成分块要对齐流协议**（index / blockType / block-end / finish），是 B 里最容易写错的部分——
   所以 B 要单独实现、单独验证（桩测：喂假流，断言"通过则原样放行 / 不通过则原文未出现且合成了 note 调用"）。
   另注意：**`finish` 之后的生成器代码不保证执行**（消费方会 break），补申明必须放在 `finish` 之前或 `finally` 里。
4. **同模型孪生独立性弱**：执行在自己的 reasoning 里已"自我同意"过，同模型换角色属弱校验。
   判"是否符合用户指令"尚可（判据是外部硬标准）；判"执行想不到的错"收益有限。
5. **延迟（阻塞式，用户可感知）**：闸门是停等的——审查期间执行侧零产出。
   工具闸门每次一个 API 来回；文本闸门导致答案不再逐字流式（"思考流 → 停顿 → 整段出现"）。
   实测每回合约 4.3 次审查 → 每回合约 4 次可感知的停顿。
   **最坏情形**：监察 API 持续失败 → 工具闸门会把回合冻住约 25 秒（5s × 5）再中断。
6. **噪音风险**：若监察变挑刺机，每回合数条意见会干扰执行。防线＝预算 + 未解决出口 + 角色提示词里的证据要求。
7. **误拦风险**（工具闸门最需要防）：监察误判会把正常工具调用拦下。防线＝预算 +
   提示词要求"没有证据不许提意见"（角色提示词里的硬约束）。
   **误中断风险**：监察 API 故障时工具闸门会主动中断对话（按你的策略），所以固定文本必须清楚说明
   "是监察不可用、不是任务失败"。
8. **"没有独立开关"的止血路径**：孪生随**本插件**启用/停用（§7/§8）。由于它是**独立插件**，
   止血 = 停用/卸载 `dsh-liubian-twin`，**记忆注入（`dsh-liubian`）不受影响**——
   v1 担心的"关掉孪生就连记忆一起停"的问题，因独立插件而不存在。
   实现时仍要把这条写进插件 README/技能文档，让人知道止血路径在哪。

### 13.6 与本方案的偏离与新增（用户逐条指示的产物）
