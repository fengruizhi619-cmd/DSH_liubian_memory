# 被炉必须保留的行为清单 v1（重构详设输入）

> 目的：被炉将按《进一步融合》决议**以多智能体为主体重构**。本清单登记现行被炉中**由真实事故换来的行为**——重构详设必须把它们列为需求（或显式说明替代方案），不允许"重写时顺手丢掉"。
> 每条四段：**行为**｜**事故出处**（日期·症状·实证）｜**现行实现位置**｜**重构需求一句话**。
> 起草：拾遗（#12752e45，被炉归属人）2026-10-06｜配套：现行代码 v0.4.0（`1a5b395`），全部行为已在产验证。

## A. 上下文与投递（对应决议现症「跨对话上下文污染」）

### A1. 投递条数上限：一次只灌最新 10 条
- **行为**：单次注入块最多 `kotatsuMaxDeliver`（10）条最新消息；块头 `deliver="merge:队列全长"` 让真实体量可见；块尾折叠提示「更早的 N 条未随本次注入显示——消息未丢失，可用 poll 或 search 查看」。
- **事故出处**：2026-10-05 管理员报「加入被炉直接把全部上下文灌入」。根因：新成员游标为 0，而 09-30 的"整段出队"口径让首次被 @ = 灌整房（实测 340+ 条）。
- **现行位置**：`collectDeliverables` + `DEFAULTS.kotatsuMaxDeliver`（v0.3.5）。
- **重构需求**：投递必须有条数上限；未读总量必须可见；必须有历史自助检索通道（poll/search）兜底。上限数值可调，**机制不可丢**。

### A2. 唤醒判据与过滤模式解耦
- **行为**：只有「@我」或「系统消息」才唤醒会话；`filter=all` 只决定自然回合里带出多少内容，**不决定要不要唤醒**。
- **事故出处**：2026-10-01 管理员报「莫名其妙被唤醒」。实证：日志 22 次出队扫描唤醒里 **15 次**前 30 秒内无一条 @（all 过滤成员被闲聊逐条叫醒）。
- **现行位置**：`hasPendingMentions`（v0.2.8）。
- **重构需求**：唤醒 = 显式点名或系统事件；任何"订阅全量"语义只影响读取广度，不得触发唤醒。

### A3. 注入体积旋钮（字符级，默认关）
- **行为**：`kotatsuMaxInjectChars` 超限时从最旧一端整条丢弃并附提示（绝不截断单条内容）；默认 0 = 不限（条数上限 A1 已是第一道闸）。
- **事故出处**：2026-10-01 实测：房间 274 条时一次唤醒最坏 46k 字符 ≈ 27k tokens；理论最坏整房出队 ≈ 121k tokens（200k 的 61%）。
- **现行位置**：`capInjectedLines`（v0.2.0 批）。
- **重构需求**：字符与条数两级上限并存；截断必须整条、必须留痕提示。

### A4. 注入提示文案由管理员逐字管理
- **行为**：唤醒/模式提示的固定文案（现值含「输出内容请尽可能简短」「需要唤醒或通知谁，直接在消息里 @对方」）。
- **事故出处**：2026-10-02 管理员先令**删**「不要随便 @」劝阻句（两处副本同改），随后又令**加**「直接使用 @」引导句——同一句话一天内两度逐字调整。
- **现行位置**：impl.mjs 两处注入模板 + `~/.dsh/skills/liubian-kotatsu/SKILL.md`。
- **重构需求**：提示词属产品面，改动须管理员逐字确认；**同一文案有多处副本时必须一处定义、多处引用**。

## B. 删除与身份（对应「账目经得起时间」）

### B1. 删除 = 跨系统单事务收口（L1+L2+L3）
- **行为**：删除账号/面板移除 = 清本地运行身份（成员/游标/副手/模式）+ 基建 `forgetSession({ retireName: true })`（解绑 + 清 session_seen + 写墓碑 + 注销名字，单事务）；服务缺席时**回执显式报"未收口"**，不静默。
- **事故出处**：2026-10-01 三人（基石/孪生/玉簪）经面板删除后停在"本地已清、绑定还在、名字未注销"的永久搁浅中间态，需人工补收口。
- **现行位置**：`removeMemberRecord` + 路由/工具两条入口同链（v0.2.2/v0.2.7）。
- **重构需求**：删除语义与入口数无关——**所有删除入口必须走同一条收口链**；部分失败必须可见、可重试。

### B2. 墓碑硬拒：删除后不得复活
- **行为**：已墓碑会话 join / mode 一律拒绝（本地墓碑 + 远端墓碑双查，远端查询**不推水位**）；唯一复活通道 = 管理员在基建侧 revive → 被炉消费 `changes` 的 lift 事件解除本地墓碑。
- **事故出处**：2026-10-01 管理员裁定「一切拒掉」；此前"自删除环"（刚建的记录被下一轮墓碑轮询清掉）在代码评审中被基建守夜人逮出。
- **现行位置**：`forgottenReason` / join 与 mode 两道门 / `infraSyncOnce` lift 消费（v0.2.5/v0.2.6）。
- **重构需求**：删除是硬拒；自动重建与显式 re-join 都不许；复活只走管理员的显式通道并留账。

### B3. 墓碑优先于降级（「离线」≠「已删」）
- **行为**：消费注册中心必须三分——**不可达**→允许按登记链降级（回落本地副本）；**身份已注销/墓碑**→禁止回落（墓碑优先于降级）；**正常**→实时解析覆盖本地副本。
- **事故出处**：2026-10-01 自曝：加固曾把 retired 的绑定行过滤掉，"已注销"与"不可达"都变成 null → 死人靠本地副本照样显示。
- **现行位置**：`registryState() → { reachable, active, blocked }`（v0.2.2）。
- **重构需求**：身份读取必须三分；两类降级在代码里不得共用同一分支。

### B4. 留言板死信标记
- **行为**：删除成员时，指向他的**未读**留言标 `status='orphaned'`（不再计入未读角标）；已读行保留（历史留档 + from_name 快照）。
- **事故出处**：2026-10-01 对账发现未读角标对已删成员永远虚高（假信号）。
- **现行位置**：`removeMemberRecord`（v0.2.2）。
- **重构需求**：收件人不存在时的未读状态必须有终态，不得永远"待送达"。

## C. 权限与面板

### C1. 权限集合运算只在服务端
- **行为**：副手开关是**意图式**（客户端只发 `{room, toggle: id}`），名单由服务端计算、校验"必须是本房间成员"后落盘并回传。
- **事故出处**：2026-10-02 管理员报「设置副手有问题」。根因：客户端那段名单数学会把**所有非副手成员**并进名单——线上实证 AIC 房间 5 人 4 副手。
- **现行位置**：`toggleRoomDeputy`（v0.3.0）。
- **重构需求**：权限集合的运算与校验永远在服务端（单一事实源）；客户端只发意图、只渲染服务端回传的结果。

### C2. 面板路由纪律
- **行为**：`/api/<包名>?op=…` 路由内**显式声明 `log`**；失败必须可见（客户端 `.then()` 必须读响应并回执）。
- **事故出处**：2026-10-01 `log is not defined` 假失败——**动作已生效、回执 500**，管理员看到失败实为成功（4 个 op 同款）；用户报障才暴露。
- **现行位置**：`mountPanelRoutes`（v0.2.1 修，协议 §12 收录）。
- **重构需求**：路由处理器的作用域变量显式化；任何"操作成功但界面报错/界面成功但操作失败"都是事故。

### C3. 客户端半边 = 注册期快照
- **行为**：client.js 改动**必须重启**才生效（F5 无效）；生效判据 = 挂载日志版本戳。
- **事故出处**：2026-10-01 移除按钮修复后的误判期（以为刷新即可）。
- **现行位置**：dsh-client-modules `reconcilePackage` 机制（协议 §10 收录）。
- **重构需求**：新多智能体前端的"改了没生效"排查第一步永远是核挂载版本戳。

### C4. 消息流滚动纪律
- **行为**：新消息只在读者本就在底部附近（<80px）时贴底；「查看更早」每次只多渲染 15 条；展开用高度差补偿 scrollTop 保持视觉原地。
- **事故出处**：2026-10-02 管理员报「一有新消息被拽到最底下 / 展开更早跳到第一条」（对照 DSH 原生 chat 的分页+视口锚定实现）。
- **现行位置**：client.js `stickBottomRef` / `expandAnchorRef` / `visibleCount`（v0.3.3）。
- **重构需求**：读者视口主权——自动滚动只服务于"跟随尾部"状态；分页展开必须锚定。

## D. 跨插件消费（服务通道）

### D1. 消费守卫必须三分：缺席 / 形态不符 / 实调失败
- **行为**：`infraSyncOnce` 对"svc 在线但缺方法"打**一次性 warn**（`shape-mismatch`），与"服务缺席"分开；`account status` 四态真调（缺席/实调 ok 报 seq/实调失败/形态不符）。
- **事故出处**：2026-10-05 Batch 1 kit 直调回归：infra v0.5.0 裸实例导致被炉 5 个消费点（含守夜人清单外的第 4 处——15s 墓碑轮询）**静默失效约 2 天**；期间删除回执还误报"服务不可用"。
- **现行位置**：`infraSyncOnce` / `infraStatusLine`（v0.3.4/v0.4.0）。
- **重构需求**：任何服务消费守卫不得把"形状不符"与"缺席"归并成同一种静默；形状不符必须进程级喊一次。

### D2. 服务提供形态走 kit 基类
- **行为**：`kotatsuBoard v1` = `new BaseLiubianService({ name, version:1, methods:{ roster, send }, kitVersion })`；挂载经 `svc.mount(ctx)`（双行日志含 via + kit 版本，基类打印）。
- **事故出处**：Batch 1 的教训制度化（协议 §19）；被炉是 Batch 3 迁入样板（v0.4.0）。
- **重构需求**：新多智能体的服务面继承 kit 基类；方法契约保持直调形态（消费方零改动原则）。

### D3. 留言板发送契约（在产消费方：便签升格流水线）
- **行为**：`send` 绝不抛、收件人受 roster 门禁（名单外拒绝**且不落库**）、`fromRef` 打 `svc:` 来源标记；`roster()` 不可达返回空。
- **事故出处**：青简流水线 12+ 轮在产依赖；"来源标记被改写"曾让收件方拿不到业务坐标（其 v0.7.1 修复）→ 契约推论：**消费方自备业务坐标字段**。
- **现行位置**：`boardService`（v0.2.9 起，v0.4.0 迁 kit）。
- **重构需求**：留言板作为多智能体部分的内部投递设施保留上述契约；收件门禁与来源标记语义不变。

## F. 历史署名与显示名

- **行为**：消息行 `from_name` 是**写入时快照**（历史显示旧名）；成员簿显示名经注册中心**实时解析**（C1，v0.4.0 起带三态）。两者并存是正确，不是不一致。
- **事故出处**：改名/删除语义讨论中反复被误读为"不一致"；协议契约 §3 已收录「历史署名冻结（快照），当前显示名实时解析」。
- **重构需求**：消息存储保留署名快照；显示名永远实时解析；两者不许互相改写。
