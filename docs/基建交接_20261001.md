### 注册表 schema（0.4.0）

```sql
identities(name PK, name_key UNIQUE, hash UNIQUE, short_id, status, workspace, note, created_at, retired_at, retired_note)
bindings(session_hash PK, name UNIQUE, bound_at, note)      -- 名字副本，改名时同事务传播
session_seen(session_hash PK, workspace, last_seen)         -- 注入钩子登记，bind 归属校验用
meta(k PK, v)
name_aliases(name_key PK, name, hash, renamed_at, note)     -- 0.3.0：旧名 → 身份
renames(id, hash, old_name, new_name, at, actor, note)      -- 0.3.0：改名账目
tombstones(id, session_hash, op, at, actor, reason)         -- 0.4.0：删除/复活事件，**只增不改**
```

### 跨插件服务通道（v0.4.0，被炉账号工具用）

按单写者规矩，写动作由基建落笔、消费方**不直写** `registry.db`：

```js
const svc = ctx.reflect.get('liubianInfra')   // 或 ctx.get('liubianInfra')
svc.version                                       // 1
await svc.rename({ ref|hash, newName, actor, note })  // → {ok, hash, name, shortId, bindingsMoved?, noop?, error?}
await svc.unbind({ sessionHash })                 // → {ok, removed, name?, error?}
// v0.4.0 删除与同步（契约 §8）
await svc.forgetSession({ sessionHash, actor, reason, retireName = false })
// → {ok, sessionHash, tombstone:true, alreadyForgotten, unbound:0|1, name, retired:false|'retired'|'already-retired', at}
await svc.liftTombstone({ sessionHash, actor, reason })   // → {ok, lifted, alreadyActive?}
await svc.changes({ since = 0 })   // → {ok, seq, identities[全量], bindings[全量], tombstones[id > since]}
```

- `rename` 的 `hash` 也接受**当前名**或 hash 唯一前缀；语义 = 工具面 `rename`（hash 不变 + 别名 + 账目 + 绑定副本传播）。
- **⚠ 会话哈希 ≠ 身份哈希（v0.3.2 修，交接首日实测）**：消费方（被炉 account 工具）传的 `hash` 是**会话哈希**＝被炉成员 ID＝`bindings.session_hash`（由 sessionId 派生），而 `identities.hash` 由**名字**派生——生产库实测 **13 条绑定同源 0 条**。`resolveIdentityRef` 已补「按 bindings 反查」一路，故 `{ hash: <成员ID> }`、`{ ref: <名字> }`、`{ hash: <身份hash全值/前缀> }` 三条都能过。
- `unbind` = **只解绑**（L2 的裸原语）。要"删除运行身份 + 墓碑"用 `forgetSession`；`unbind` 保留给不需要墓碑的场景。
- **`forgetSession` 的 `retireName` 默认 `false`**：名字独热不回收 ⇒ retire = **永久烧掉一个名字**。管理员裁定的产品语义是「删除账号 ⇒ 一并 retire」，由消费方**显式传 true**（接口默认 ≠ 产品语义，两处分开写）。
- 🔴 **`liftTombstone` 的顺序**：显式再注册路径必须**先 lift、再建自己的本地记录**——否则消费方下一轮轮询看到仍是 `forget`，会把刚建好的本地记录当墓碑清掉（**自删除环**）。
- 错误一律折成 `{ok:false,error}`，不抛。
- 挂载形态：优先 `ctx.provide`（cordis 标准形），回退 `ctx.reflect.provide`；两者皆无 → 记一条 warn 且服务缺席（消费方应显式报错，不得静默降级为"只改本地名"）。

1. **热更姿势按归属选**：bundle 归属插件**不要**用 `uninject + inject`（会写 `disabled` 残留、删 junction）；改 `impl.mjs` 走「touch profile patch 触发重装配」。纯注入包才用 uninject+inject。判据看 profile `dependencies ∩ bundles`。

3. **单写多读**：只有基建写 registry.db；消费方一律只读打开（`mode=ro`）。别用共享 DB 写做跨插件同步（用工具/服务通道）。
4. **改名不变式**：hash 是账号 ID 不可变；name 可变。旧名不可二次注册（hash 由名字派生）。拒绝路径零写入、写入包事务。
5. **看门狗阈值**：本机空载稳态私有提交 ≈10.8GB，**阈值必须显著高于它**（现 12288MB）；阈值低于稳态 = 周期性杀服务 → 每次击杀都是整模 GPU 重载尖峰（2026-10-01 旧 embed 看门狗因此全天击杀 80 次，凌晨无任务也每 5 分钟一次——「没向量任务却跑满 GPU」的根因）。
6. **ensure 防重复拉起**：spawn 前必须查存活进程（`serverPids`），否则同端口多实例抢 8082、每个都是整模载入。
7. **提交与文件的 BOM 坑**：Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会给文件加 BOM；提交信息走 `git commit -m '单引号'` 或 write 工具。**判定提交是否带 BOM 必须看原始字节**（`git cat-file commit <hash>`），`git log --format=%B` 会吃掉 BOM 造成假阴性。

    - **事故**：`watchdogTick` 旧版第一句是 `if (!up.ok) { overLimitStreak = 0; return }` —— 服务不在线就**直接返回、什么都不做**；它唯一动作是"超限则杀"。于是 llama-server 一崩就**再没人拉起**，直到下次 DSH 重启。当晚 **≥21:04 → 22:35（≥90 分钟）无人察觉**，证据是记忆插件 error.log 三次 `嵌入请求失败（fetch failed）`（21:04 / 21:57 / 22:24）；而失败日志里**没有一行**记录服务是怎么死的。
    - **修法三道**：① `watchdogTick` 探活失败时判 `shouldRecoverLiveness(...)` → 无进程且非显式停过就走 `ensureInFlow` 恢复；② 新增 `explicitStop` 标记（`embed-stop` 置 true、任何 `launch`/`embed-ensure` 清 false）——**"谁关的"必须可分辨**，否则自动恢复会跟人抢；③ `ensureInFlow` 的"已在后台拉起"改为按 `launch()` **实际返回值**记账，并加 3s 存活复查——旧版 spawn 失败时**同样报成功**，是典型静默失败。
    - **判据抽成纯函数** `shouldRecoverLiveness({probeOk, pids, explicitStop, autoEnsureOnLoad})`，桩测 7 格（含"事故回放"格）。规则错一次就是"服务死了没人管"，必须有可跑用例。
    - ⚠ **运维含义**：想让服务**保持关着**（省显存）必须用 `embed-stop`（会被标记为显式停止）；直接杀进程会被看门狗拉回来，这是有意的。
17. 🔴 **llama-server 输出被丢弃 = 死因无从查起（v0.4.0 内已修）**：`launch` 旧版 `stdio:'ignore'`，子进程 stdout/stderr 全丢——§5.16 那场静默死亡**查不到任何死因**。现改为落盘（追加写，键 `serverLogFile`，默认 `~/.dsh/liubian-infra/llama-server.log`），每次拉起写一行时间戳分隔；**落盘失败退回旧行为**（绝不因为写日志而拉不起服务）；置空该键可显式退回丢弃。
    - 另：存活恢复只解决"死了没人管"，**不解决"为什么老死"**——修复后仍观察到短命实例（一次恢复出来的实例 <1 分钟即消失）。根因未定，落盘就是为了下一次能查。
18. **账目 actor 会丢"谁做的"（v0.4.0 内已修，拾遗实测）**：工具面 `forget`/`revive`/`rename` 原样取 `args.actor || null`，调用方不写 actor 就丢归属（实测三条墓碑 `actor=null`）。已补 `resolveActor(db,{actor,exec})`：**显式 actor > 调用方会话绑定的身份名 > null**（与 register/bind 的归属推导同源）。**"做了什么"与"谁做的"在账号体系里同等重要**——三处一起修，只修一处就是新的两处真相。

20. 🔴 **`/health` 会说谎：探活 ≠ 能干活的（2026-10-02 青简实测逼出，已修）**：
    - **现象**：llama-server 进入**僵死态**——`GET /health` → **200 {"status":"ok"}**，但 `POST /v1/embeddings` **20s 超时、复测 90s 仍超时**（实例跑了 190 分钟、私有提交仅 4157MB）。此时 `probe()` 判"在线" → **看门狗既不告警也不恢复**，`embed-status` 也报"在线"，而所有消费方都在等满超时。
    - **性质**：与 §5.16 同族——**探针只验了"HTTP 活着"，没验"活儿能干"**。这也是"探针本身要先被验"的又一例。
    - **修法**：新增 `probeEmbed(cfg)`——真发一次 `POST /v1/embeddings`（`input:['ping']`），判据＝**200 且向量维度 > 0**（不硬编码 1024，换模型时维度会变），超时上限 `probeEmbedTimeoutMs`（默认 8000ms）。
      ① **看门狗**：`/health` 在线之后**必须过这一关**；连续 **2 轮**实调失败 → 判僵死 → `stop`+`launch`（与内存超限同一套防抖）；
      ② **`embed-status`**：把"探活"与"实调自检"**分开显示**——`[OK] 在线且实调可用` / `[可疑] /health 在线但实调自检失败`，**让"在线"不再有歧义**；
      ③ 桩测 3 格（不可达端口不抛 / 超时口径 / 活体正例）。
    - ⚠ **修复日的现场**：复核时那个僵死实例（PID 31404）已被换掉（现 PID 更替），真嵌入 11ms/1024 维——**现象无法复现**。所以这条是**按形态修的，不是按复现修的**：`/health` 与真调分离是明确更严的判据，即使原实例的死因仍未知。
