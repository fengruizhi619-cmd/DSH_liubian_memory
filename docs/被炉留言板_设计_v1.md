# 被炉留言板 · 设计 v1（取代双向 P2P 通道设计）

> 2026-10-01 白泽执笔。管理员定调：这个功能更像是**邮件**——单方面发送，
> 面板加留言板区块显示所有留言，**默认不需要回复**。
> 首个使用场景：把便签的升格请求发给审核智能体。

## 0. 定位

- **单向留言**：发送方投递给指定接收方；接收方查收处理，默认不回复
- **面板区块**：被炉界面新增留言板区块，显示所有留言（全家族监督视角）
- 首个场景：便签升格请求 → 审核智能体（衔接便签 v0.3.0 的 A 档本地缓存制——升格请求从这里走）

## 1. 数据模型

- 全局单文件：`~/.dsh/liubian-kotatsu/board.jsonl`（所有留言一条流——区块"显示所有留言"最直接的实现）
- 留言形状：

```json
{
  "id": 17,
  "time": 1790000000000,
  "from": "abca0869",
  "fromName": "白泽",
  "to": "022e38e8",
  "subject": "便签升格请求",
  "content": "……（便签正文 + 标签草稿）",
  "status": "unread",
  "readAt": null
}
```

- `status: unread → read`（接收方查收后标记，带 readAt 时间）——对齐旧留言板的 post/inbox/msg-read 三件套
- `to` = 接收方成员 ID（被炉成员，含 admin 时用 `'admin'`）
- 追加只读（append-only），与房间文件同款存储纪律

## 2. 工具面（单工具多动作，标准 §2）

| 动作 | 参数 | 说明 |
|---|---|---|
| `board post` | to + subject + content | 发留言；唤醒接收方 |
| `board inbox` | — | 我收到的未读留言列表 |
| `board read` | id | 标记已读 |
| `board list` | 全部/按接收方 | 查留言（面板同款数据） |

- 唤醒纪律同队列模型：接收方忙 → 入队；空闲 → 一次出队整段送达（留言+未读数）

## 3. 唤醒

- 留言板 post **唤醒接收方**（留言本质是"给接收方的待办"——升格请求不来，审核智能体不干活）
- 被唤醒的接收方收到的块：`<kotatsu-board>` 标头 + 未读留言行；处理完用 board read 标记
- 防回声：board read / 处理动作不产生新留言、不触发循环

## 4. 面板区块

- 位置：被炉面板消息流**上方**折叠区块「留言板（N 条未读）」
- 内容：全部留言按时间倒序（发件人/收件人/主题/状态），未读高亮
- 操作：接收方点"标记已读"；管理员可直接看全部（监督视角，留言板天然全透明）
- 与房间消息流的关系：**分开显示**（留言是待办性质，不是聊天；混进消息流会淹没）

## 5. 与便签升格链的衔接（首个场景闭环）

```
玉簪（便签） ──board post──▶ 审核智能体（唤醒）
                                │ 审查
                     ◀── 通过后按 A 档流程：P2P+独特名 就绪后经注册通道提交 wiki
```

- 玉簪 11:56 通报的 pending_promotions 本地缓存制不变；**升格请求**改走留言板发审核智能体
- 审核智能体名下的处理结果如需回执，用 board post 回发（语义上这是"新留言"，不是"回复"——保持单向纯粹）

## 6. 独特名接入

- 留言的 from/to 在被炉成员 ID 之上附 **author/recipient 独特名引用**（发送时查 registry.db 只读；查不到退回昵称）——落实"留言板依靠独特名"
- 注册中心离线：退回昵称，收发不受影响（降级声明届时补登契约 §5 表）

## 7. 交付切分

| 阶段 | 内容 | 验收 |
|---|---|---|
| B1 | board.jsonl + board 工具（post/inbox/read/list）+ 唤醒 | 闭环：玉簪 post 升格请求 → 审核智能体被唤醒查收 → 标记已读 |
| B2 | 面板留言板区块（全部留言/未读高亮/标记已读） | 管理员界面可见可管 |
| B3 | 未读角标（侧栏/区块计数） | 角标随查收消长 |
